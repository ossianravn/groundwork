# Density contract and Overview audit

Status: implemented and checked, awaiting user review, 2026-09-25. Part of the Overview foundations review.

Density changes the space occupied by working with content. It preserves text legibility, hierarchy, recognizable symbols and the space needed to understand a chart. Apply it through shared relationship tokens, not a page zoom or independent reductions on whichever component was touched last.

The component-specific approach follows [MUI density guidance](https://mui.com/material-ui/customization/density/); the distinction between internal and layout spacing follows [Carbon spacing](https://carbondesignsystem.com/elements/spacing/overview/). Values below are this project's decisions, not values mandated by those references.

Routed project create/edit follows card insets, stack gaps and standard field/control roles. Name/Description and Owner/Date share two aligned columns, following [form field widths](design-system.md#form-field-widths); the grid stacks in reading order when its container cannot accommodate both. Content proportions are independent of density. Labels, errors and feedback retain readable type; the footer follows content/control gaps and wraps actions when necessary. Its portalled Owner menu inherits the shared menu role. Narrow insets and coarse-pointer targets retain the shared responsive rules.

## Implementation rule

When introducing or changing geometry, classify it as density-responsive spacing, content-sized geometry, or an intentionally stable semantic/readability dimension. Reuse the corresponding token; compare both densities when their geometry or shared spacing is affected, including relevant portalled overlays. Select other checks through the [repository verification policy](../AGENTS.md#verification-and-completion). A difference in pixel size is not itself a defect; an unexplained exception or a fixed value bypassing its role is.

The [narrow-screen composition rules](design-system.md#narrow-screen-composition) define how these tokens compose at limited widths.

## Verification

Analytics addition (2026-09-27): cards, filters, data views and legend gaps reuse card/control/item tokens. The primary plot is 20rem on desktop and 16rem on narrow screens; bar rows derive height from measured line height, and the donut has a stable readable diameter. These encode chart readability, not density reductions. Names and numbers stay readable; narrow layouts stack breakdowns rather than compressing chart labels.

Inbox (2026-09-27): list rows, thread messages, reply form, toolbar and notification drawer use item/card/section/control tokens. Text, unread dots and avatars preserve semantic sizes. The workspace fills the viewport below the header with no outer card or page gutters; desktop list/thread scrolling stays inside it, while narrow layouts use page scrolling. The 65ch reading measure, 36rem compose dialog and panel proportions are content/layout choices. Row and composer insets respond to density together.

Computed dimensions and rendered compositions were compared in Chromium for both settings. Page, Appearance, form, command search, filter/column menus, project details and collapsed navigation were checked. Narrow/touch targets, enlarged text, saved density and consequential focus/feedback were checked. Future component changes should extend this inventory where they introduce a new density role.
