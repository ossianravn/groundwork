# Central styling and customization

Status: Overview/mobile visual direction accepted as the working baseline, 2026-09-25. The implementation uses React/Vite, Tailwind 4 and shadcn/Base UI. Other future surfaces and playground features below remain proposals, and recorded platform/accessibility limits remain open.

The user's portability goal is recorded in [framework portability](framework-portability.md). Shared primitives, patterns, page views and theme tokens remain ordinary React/CSS; framework-specific routing and rendering integration belongs to the demo host.

Centralize visual decisions at their owners. Keep page-specific layout close to the page. A single enormous stylesheet or universal configurable page component would make customization harder.

Use the [working reference shortlist](sources.md#working-reference-shortlist--2026-09-26) to choose an established composition for the affected workflow before adapting it. It distinguishes the primary visual baseline, complete shadcn examples, interaction guidance and discovery catalogs. A set of valid primitives is not evidence that their arrangement is coherent.

Apply [progressive disclosure and action surfaces](ux-decisions.md#progressive-disclosure-and-action-surfaces) before composing controls: decide what belongs in the current view, what appears in context, and what is reached through an overflow menu, disclosure, popover, dialog, sheet or page. The UX guidance owns these choices; shared primitives and tokens own their implementation.

## Ownership model

| Layer              | Owns                                                                                      | Example changes                                      |
| ------------------ | ----------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| Foundation values  | Font families, type scale, spacing scale, radii, shadows, motion durations/easing, widths | Change the overall visual character                  |
| Semantic tokens    | Surface/text pairs, emphasis, border, focus, status, chart and sidebar roles              | Change a brand without recoloring individual pages   |
| Primitive variants | Button, field, badge, card, dialog and table treatments/states                            | Change every control of the same kind consistently   |
| Shared patterns    | Page header, toolbar, form section, empty state, metric card, data view, prose            | Change recurring compositions once                   |
| Shells             | Navigation dimensions, content containers, persistent regions, responsive transitions     | Change application or public layout structure        |
| Pages              | Content order, data, feature-specific composition                                         | Add a workflow without inventing a new visual system |

Use shadcn's semantic CSS-variable contract as the base. Colors pair surfaces with foregrounds; theme changes override tokens rather than rewriting component classes. Its theming documentation explicitly supports this approach. [shadcn theming](https://ui.shadcn.com/docs/theming)

Tailwind 4 exposes shared design values through its theme system; runtime semantic variables use the inline mapping in `src/kit/styles/kit.css`. Regular custom properties remain useful for values that do not need utilities. These are different responsibilities, not two competing token stores. [Tailwind theme variables](https://tailwindcss.com/docs/theme)

## Iconography

Use Lucide for interface actions and objects. Recognizable provider choices use their actual brand marks beside visible labels, not generic substitutes or text-only approximations. The installed Lucide version does not include provider logos; reusable marks live in `src/components/brand-icons.tsx`, with provenance in `src/assets/brands/README.md`. Preserve brand colours where required, use theme-aware foreground for monochrome marks, and let the Button own icon size, gap and alignment through `data-icon`. Icons repeating a visible label are decorative to assistive technology. Add icons where recognition benefits the task, rather than decorating every label.

## Code boundaries

The code is split into a reusable **kit** and the **Tandem demo** that exercises it (user decision, 2026-09-28). Another project adopts `src/kit/`; everything else is demonstration.

    src/kit/
      ui/                  # owned shadcn primitives and their variants
      data-table/          # facets, pagination and column options
      rich-text/           # editor and safe document rendering
      ai/                  # chat components for AI SDK UI (presentational)
      shell/               # public and workspace shells, account menu, brand mark
      theme/               # preference application, persistence, presets, fonts
      lib/                 # utilities
      styles/kit.css       # Tailwind entry: tokens (theme.css), mappings and kit styles
    src/components/        # Tandem-domain components, brand and shell content
    src/features/          # page views and domain composition
    src/demo/              # fixtures and local state
    src/app/               # routes and host bindings
    src/styles/demo.css    # demo entry: imports kit.css, then feature styles

Rules, each enforced by a check:

- Kit code imports nothing from `@/app`, `@/features`, `@/demo`, `@/components` or `@/styles`, and never imports the router (ESLint, `src/kit/**`).
- Kit stylesheets style only classes that kit components render and import no demo stylesheet (`src/kit/kit-boundary.test.ts`). A demo class in a kit stylesheet belongs in the matching `src/styles/` file.
- Shells contain no product content. The host supplies brand (`ShellBrand`), destinations through its own `LinkComponent`, navigation items and actions, account menu items, breadcrumbs, search and footer content. [`demo-workspace-shell.tsx`](../src/app/demo-workspace-shell.tsx) and [`tandem-public-layout.tsx`](../src/components/tandem-public-layout.tsx) show the demo's configuration; [`tandem-brand.tsx`](../src/components/tandem-brand.tsx) is the one place to rebrand.
- Demo styles load after kit styles, so equal-specificity demo rules refine kit defaults. Page-level patterns (`page-heading`, `page-content`) and feature views remain demo-owned until they are promoted with a kit component.

One stylesheet entry can import cohesive files. It does not imply duplicating token definitions across them.

**Primitive styling ownership (2026-09-28).** A shadcn primitive's own appearance (size, padding, typography, overflow and responsive variants) lives in its component classes, expressed with tokens (`min-h-(--control-height)`, `p-(--item-padding)`, `max-md:`, `pointer-*` variants or token media rules). Kit stylesheets hold tokens, shells and patterns. A pattern may still position a primitive through its own class (`[data-slot="sheet-footer"].panel-footer`, `.facet-options`). The one global exception is the `forced-colors` block in `responsive.css`: its focus outlines must outrank component utilities such as Button's `outline-none`, so it stays unlayered. `src/kit/kit-boundary.test.ts` rejects any other unscoped `[data-slot]`/`.ui-button` rule in kit CSS. Density still works through tokens: `--control-height`, `--control-padding-block` and `--control-font-size` change by density, width and pointer in `theme.css`/`responsive.css`, and components read them.

**Single token source (2026-09-28).** `theme.css` is the only file that defines token values; `responsive.css` may only reassign tokens by media query. `kit.css` holds the Tailwind entry, the `@theme inline` mapping and base element styles. The shadcn CLI writes a generated token block into `kit.css` (the `components.json` CSS path); move any values it adds into `theme.css`. The boundary test fails while semantic tokens are defined anywhere else. The Appearance preview illustrations keep fixed colors on purpose, because they depict Light and Dark regardless of the active theme.

Keep every new or enlarged hand-maintained code file within the user's 300-line limit; split by responsibility, not arbitrary line counts.

**Workspace page frame (2026-09-28).** The top bar's current breadcrumb item is the visible page title. Section pages (Overview, Projects, Inbox, Analytics, Activity, Settings) keep an equivalent screen-reader `h1` and add no visible heading or subtitle row. A page's primary action and short context go into the top bar through the kit's `PageActions`/`PageAction`; `PageAction` shows only its icon on narrow screens while keeping its label as the accessible name. Controls that scope the whole page (Analytics filters) stay in the content and lead its first section header, beside the date range. Record pages (project detail and editor) keep their content heading because it carries editing and status. Primary data views sit on the canvas (`ProjectsTableView surface="plain"`). Overview shows its snapshot as one metric strip (hairline dividers, no icons), sets the chart and activity as open sections divided by a hairline, and keeps the Projects table as its single framed surface. Analytics follows the same composition: the chart, then By project and By contributor as open sections divided by hairlines. `src/styles/open-sections.css` owns the shared open-section treatment; each page sets its own dividers. The Activity feed sits open at a 60rem reading width. The project form (editor, new project and its reference examples) sits open on the page at 60ch: inputs are the only framed elements, and hairlines divide the fields, the optional Tags and links, and the actions. A project page keeps the shared page frame and left edge, caps its contents at 76rem, and keeps details and activity open with its progress as the single framed panel; its activity omits the project's own name and shows dates under each event; the project sheet shows progress as an open section, and Mark complete is a normal-width action followed by its consequence. The sidebar shows the workspace as a plain row and the demo notice as one line with Reset.

**Colour with meaning (2026-09-28).** Records get identity colour, surfaces don't. A project's colour is chosen in the project editor (six swatches, named for screen readers; new projects start on the next colour in rotation) and shows live beside the editor heading. Wherever a project is named as a link in running text (Activity, Overview's recent activity), a small colour mark precedes the name, and the name is ink with a quiet underline rather than accent-coloured; record titles (project sheet, project page, editor) carry the same mark. `theme.css` defines six categorical hues (`--hue-*`, light and dark). A project's hue marks its dot (a small rounded square, distinct from round status and unread dots), its progress bar and, later, its chart series; related projects appear as a dot plus muted name rather than a bordered pill. Grey fills no longer separate regions: table headers, card footers (the kit `CardFooter` keeps only its hairline) and comparison groups use type and hairlines. Inbox rows read in three lines (sender and project, subject, preview) with dividers inset to the text column; the empty reading pane only orients, since the top bar owns New message. Inbox marks unread with the dot and title weight, and the open conversation with a quiet surface, plus a forced-colors outline. Charts use the same palette: `--chart-1`…`--chart-5` are hues and never follow the accent, so every accent (including Neutral and Teal) keeps series distinct; a single primary series, such as the completion trend, uses the accent explicitly. Per-project series use the project's hue. Daily counts are bars, not a line: zero days stay visibly empty, earlier days sit at half strength and the snapshot day at full, and the legend swatch is square to match. Bars are thin with rounded ends.

**Dates (2026-09-29).** Dates cross component boundaries as ISO strings (`src/kit/lib/iso-date.ts`); pickers convert to `Date` only inside. `DatePicker` is the form control for a single date: give its `FieldLabel` an id and pass it as `labelledBy`, so the trigger's name is the label plus the chosen date. Inside a `Field` the trigger fills the column like a Select. `DateRangePicker` suits report scopes: pass `latest` and `maxDays` to keep ranges within real data. In a chart header it uses the ghost variant, so the range reads as the chart's date line and opens the calendar. Calendars start weeks on Monday (`en-GB`), matching the demo's date formatting.

**Feedback primitives (2026-09-29).** The kit's `ToastProvider` mounts once in the root layout; call `useToast().add()` with a title, an optional description, `type` (`success` or `error`) and an optional action. Use a toast to offer Undo after a change that applies at once, or to report an outcome the person cannot see where they acted. Keep blocking errors and retry inline, and put Undo inline where an outcome region already exists (table bulk actions). `Button` takes `loading`: the label keeps its space under a spinner, so neighbouring controls do not move, and the button stays focusable with `aria-busy`. Only asynchronous work uses it; the demo's saves are immediate outside the Slow save gallery scenario. `Progress` draws every completion bar; set `--progress-color` to tie it to a record (projects use their hue) and state the value as text. `Switch` is for on/off preferences that save; `Checkbox` stays for selecting records and agreeing to terms. `Kbd`/`KbdGroup` show shortcuts; the search trigger shows its hint only on wide screens, and `aria-keyshortcuts` remains the accessible statement. `RouteProgress` belongs to the host's root layout and appears only after 150 ms.

**AI and chat (2026-09-30).** `src/kit/ai/` holds presentational chat components shaped after the AI SDK's message model: they take status strings, text and handlers, and import nothing from `ai`, so any client can drive them; the demo drives them with `useChat`. Replies render as prose without a bubble at a reading width, and the person's prompts as secondary bubbles. `MessageResponse` styles every markdown element with kit classes and hands fenced code to the kit `CodeBlock`; hosts pass `renderLink` to route internal links. `CodeBlock` highlights with Shiki's CSS-variables theme, so syntax colours are the `--syntax-*` tokens in `theme.css` (each keeps text contrast on `--muted`, where code sits). `Shimmer` marks short working labels such as Thinking… and stops under reduced motion. Streaming text is never announced token by token: the transcript's log is silent and a status region announces the finished reply once. Controls that disappear when used (suggestions, Regenerate, Try again) hand focus to the composer. Agent activity sits above the answer in the order it happened. Reasoning and Chain of thought open while working and fold away when done; a person's own toggle wins, via `useAutoOpen`. Tool rows stay closed unless they fail, and show the AI SDK state as a labelled badge. Citations are quiet numbered pills whose hover card only repeats the Sources list, because hover cards are not keyboard-reachable; AI Elements' citation carousel is deliberately not used. `ResponseLinkContext` carries the host's link renderer to responses, sources and citations. An assistant never changes records without a Confirmation: it follows the plan it acts on, names the change in its title (Add 5 tasks to Mobile app?), lists the declining action first and the approving one by what it does, and records the outcome in place of the actions. A Plan holds no actions of its own. Questions and approvals never take focus when they appear; the status region announces them. While a decision is pending, new messages queue. The composer is one rounded surface (radius × 2.25) with a hairline border and a light shadow, and a soft brand ring on focus. Tools sit in a row under the text: + at the start; context, model and a round send button at the end. Keyboard hints belong in the send button's tooltip, not on screen. Attachments are chips (thumbnails for images) whose remove button sits inside the chip. Controls that only matter on demand, such as Restore between turns and the history row menu, appear on hover or focus with a fine pointer and stay visible on touch screens.

**Precise direction (2026-09-28).** The kit default separates action from brand. `--primary` is ink (near-black in light, near-white in dark) for primary buttons and selected controls; the accent preset (Indigo, Teal, Neutral) sets `--brand`, `--brand-foreground` and `--brand-soft*`, which colour links, focus rings (`--ring`), the single-series trend and progress fallbacks. The canvas and sidebar share `--background`; hover and selected surfaces use a neutral `--accent`. Cards carry a 1px `--border` ring plus a faint shadow so they hold their edge on the white canvas. The theme playground edits the brand tokens and checks link contrast on the background. Check every colour change under Indigo, Teal and Neutral in light and dark.

**Tandem brand layer (2026-09-28).** The public site may carry a product identity the workspace does not. `src/styles/public-brand.css` (demo only) sets the Bricolage Grotesque display face on the home headline and public section headings, and places the product screenshot on a fixed Tandem-blue stage with a lime label and soft conic shapes. The screenshot hangs below the stage (`--stage-hang`, 1.25–3rem) with its own rounded frame and shadow; the stage is a separate decorative element (`.public-stage`) so its blurred shapes stay clipped while the screenshot is not. The same layer sets the Pricing and Product page headings and plan prices in the display face, and puts the recommended plan (Team) on the Tandem field; its tokens are reassigned inside that card so text, rules and the lime button follow. Resource pages (Help, Articles, Changelog, Contact) use the display face for titles and release headlines; Help's topics are open columns under a 2px ink rule with hairline-separated links, and its search is taller through a local `--control-height`. The brand tokens live on `.public-site`, and the file loads after all other public styles. The public layout fills the viewport, so short pages keep the footer at the bottom. Below the hero, Home uses one three-column grid (`src/styles/public-home.css`): the features fill its columns, each with a tile tinted in a project colour that shows a close-up of the real screen; the questions heading takes the first column and the list starts on the second column line; and the newsletter closes the page as a Tandem-field panel at the content width, with tokens reassigned inside it so the form, text and lime button follow. The stage colour is Tandem's identity and deliberately ignores the accent preset; the kit ships no display face.

**Motion (2026-09-28).** `--motion-fast` (150ms) and `--ease-standard` time hover transitions on navigation, rows and the account trigger, and a short fade when switching Table, Cards and Board. `responsive.css` reduces all motion when the person asks for it.

## Token scope

- Preserve shadcn roles for background/foreground, cards, popovers, primary/secondary, muted/accent, destructive, borders, inputs, rings, charts and sidebar.
- Add success, warning and information roles only where the shared patterns need them. A status includes a textual label or icon as well as color. An increasing metric is not automatically good.
- Typography owns body, headings, labels, prose and numeric presentation. Spacing and widths provide consistent page gutters, section rhythm and reading measure.
- Density owns control/row spacing, not text illegibility or removed hit areas. Comfortable is the proposed default; compact is a deliberate data-view variant.
- Compact metadata footers use less vertical padding than the card body while retaining its horizontal alignment. Size the band around the actual row and action target; Projects cards use the 8px control gap above and below rather than repeating the body inset.
- Motion has a reduced-motion rendering path. Forced-colors mode is an environment to support; a custom high-contrast preset is a separate optional feature.
- Overlay stacking belongs to the primitive system. Avoid arbitrary page-specific z-index escalation.
- Sticky header height, surface opacity and backdrop blur have shared tokens in `src/kit/styles/theme.css`. `data-header-surface` selects Glass, Solid or System; the last follows reduced-transparency preferences. Table row height derives from the shared control-height and density tokens so filtered results can reserve the same footprint without duplicated measurements.
- Glass uses a 20% card tint and 16px backdrop blur, following the [shadcn-admin header](https://github.com/satnaing/shadcn-admin/blob/main/src/components/layout/header.tsx). The previous 82% tint hid most of the effect. Header navigation text uses foreground rather than muted foreground because its backdrop changes during scrolling. Keep the effect on the header surface, not element opacity or a filter on its children. Unsupported backdrop filtering, Solid mode, System with reduced transparency, and forced colors retain an opaque surface. See [MDN backdrop-filter](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/backdrop-filter) for transparency and backdrop-root behavior. Assess actual scrolled content; a solid page at scroll position zero cannot demonstrate the glass effect.

Token names define stable meaning. Component variants can express intent such as destructive or quiet. Pages may compose layout utilities but should not override a Button's colors, type or focus style at each call site.

Control widths follow visible content and shared padding. Filter triggers show a count only when there is an active selection; they do not reserve an invisible count slot. Content changes may resize a control or wrap the toolbar. A width constraint needs a concrete layout, data-format or interaction reason. Address table-column resizing and document-scroll jumps at the table/result layout, rather than imposing empty space on unrelated controls.

### Form field widths

Size fields for the expected content before choosing the enclosing card or grid. A short date, quantity or person selector must not stretch to occupy spare space. Use a stable width appropriate to the format or typical values, with room for padding and affordances; retain normal editing/scrolling for longer valid values. Do not add a character limit to justify a layout. Empty fields must retain their intended size, and typing should not cause distracting horizontal movement.

Compose related fields together before setting individual widths. Use shared column edges and align labels, controls, errors and actions; merely narrowing separate fields can leave a disjointed form. In project create/edit, Name and Owner share the first row, with Description and Due date below them. Name/Description occupy the wider column; Owner/Date share the narrower column. The card bounds the whole composition and the grid stacks in reading order when available space cannot support both columns. These are content and layout decisions, not universal field widths.

Review empty and realistically populated forms at desktop and narrow widths. Judge both expected input proportions and the complete arrangement: related fields should use available space coherently, without ragged edges or unnecessary rows.

Allow compound labels such as Description (optional) to wrap. On narrow project-editor pages, keep horizontal page/card gutters at 16px and native date-input padding at 10px as text enlarges; expendable whitespace must not displace the date segments or picker. Text and control heights continue to scale normally.

### Controls, panels and action feedback

- Menu item icons are 16px like the navigation's, muted at rest and foreground when highlighted; the dropdown primitive sizes them, so callers pass bare Lucide icons. A menu opened from a full-width row (the account menu) is at least as wide as that row, so the two align. The context menu reuses the dropdown's items and styling: an item's context menu repeats the actions of its visible menu button (board cards) or its row's own controls (table rows), never holds actions found nowhere else, and hands focus to the inspector through the item's inspect button. Hover cards preview a link's destination (a person's role and work) and repeat nothing the page depends on.
- Contextual project badges show the project name with a quiet outline and transparent background; do not add an initials tile or avatar. Initials avatars identify people. Existing project-code marks in project tables are a separate pattern. Compact project dates in Cards and Board share a calendar icon plus the date; the accessible label retains Due.
- Treat a section heading and its explanatory sentence as one reading group. Keep the sentence directly beneath the heading at a bounded measure unless it belongs to a separate, clearly structured column. Counts belong beside their heading or results control, not in a disconnected extra row. Analytics metric labels consistently use Completed tasks; prose may retain natural sentence grammar.

- Hover does not change border color, thickness or geometry. Use surface or foreground feedback consistently across choices, buttons and fields. Selected, invalid and keyboard-focus states retain their distinct indicators; pointer hover must not imitate them.

- Visual preference choices are radio controls. Their resting frames share the `--input` border with Select triggers, inputs and outline Buttons; `--border` belongs to structural containers and dividers, not the interactive choice boundary. Selection uses a 2px `--foreground` edge (drawn inside, so neighbours do not shift) and a consistent checkmark kept inside the choice: a small badge in a preview's top corner, or an inline check before a text-only label. Accents are shown as the colour itself, a swatch that gains a ring and a centred check when selected, without a tile around it. Keep keyboard focus distinct. Color samples communicate the available accent, while the selected marker stays neutral across palettes. Compare unchecked, hover, checked and keyboard-focused peers together before signing off. Labels beneath visual samples remain part of the clickable radio label.

- Visual-choice previews form one surface with their containing control: let the outer boundary clip the graphic, without an inset rounded frame that merely repeats it. Keep spacing inside the illustration separate from spacing around it. A nested container needs a distinct grouping or interaction purpose. For peer swatch/label choices, compare leading insets and baselines across different label lengths; independent centering does not establish alignment. Apply these checks to prototypes as well as production controls.

- Inputs, Input Groups, textareas, Select triggers and outline Buttons follow the flat [shadcn Base Input Group](https://ui.shadcn.com/docs/components/base/input-group) treatment: a shared subtle `--input` border, transparent light surface and `input/30` dark surface, with no resting drop shadow. The approved resting treatment uses shadcn's neutral input values: `oklch(0.922 0 0)` in light mode and white at 15% in dark mode. Distinct semantic roles for `--input` and structural `--border` do not require a darker field boundary. Adjust the shared token rather than individual fields. Shared radius and size variants control geometry. Hover/open actions use the muted surface; selected, focus and invalid indicators remain distinct. Popover content retains its overlay shadow. This user-directed correction supersedes the earlier blanket darkening for border contrast; the historical 3:1 input-boundary measurements no longer describe the resting style, and reference matching is not an accessibility-conformance claim.
- Faceted filters use a plain Plus icon in muted foreground, foreground labels and explicit selected counts. Status/Owner select which **rows** match. **Columns** (formerly View) toggles which optional **columns** are visible; hiding a column does not clear its row filter. Keep this distinction in control labels rather than adding explanatory copy to the toolbar.
- Checkbox outlines use the stronger, independent `--control-indicator`: the empty box communicates unchecked state. Do not lighten this state indicator when adjusting the resting field boundary. Verify against the actual fill and surrounding surface when either token changes.
- Primitives own their focus rings. The global base-layer outline is a fallback for plain links and regions, not a second indicator over an input's ring. Input Group delegates focus to its shell, including command search. Forced colors uses a system Highlight outline; selected command options and focused Select options stay identifiable when shadows and background colors are replaced. The keyboard chart surface has an explicit focus boundary.
- Bounded lists scroll in the kit ScrollArea (overlay scrollbar, native scrolling, edge-fade variables); position it through a wrapper, as Base UI keeps its root relative. Phone-width choices that would otherwise need a row of popover buttons open in a bottom Drawer; FacetDrawer does this for data-table facets.
- Popovers use Base UI's fixed positioning, sticky collision handling and available-space variables. Bound the popup itself and permit vertical scrolling; document overflow alone cannot detect a clipped portal. Search, filters and Columns retain accessible options and return focus to their own triggers.
- Dialog title/action rows participate in normal layout. Search places its Close action beside the input instead of over it. Dialogs keep a bounded title/Close grid and a footer with the same inset. At narrow widths their 16px outer/content insets stay in CSS pixels under text enlargement, leaving room for readable content; optical close offsets stop before the focus ring reaches the clipping edge.
- `PanelHeader` composes the shadcn Sheet title, description and close control in normal layout. Project details and Appearance share it. The title and close control occupy one row, with the description underneath. The project name already identifies the record; a redundant monogram above it adds no information. `--panel-padding` owns the header/body/footer inset, with the panel rules in `styles/panels.css`.
- Align the close icon's box to the content's right edge and center it vertically with the title. Its larger hit area extends into the existing inset, using the difference between the shared control and icon sizes; retain the density/mobile target sizes. Evaluate visible glyph alignment separately from hit-area alignment.
- Sheets occupy the full browser viewport through Base UI's Dialog Viewport. While mounted, the shared Sheet boundary releases the root's reserved scrollbar gutter and preserves the body's width using the viewport width minus that measured gutter. Preserve geometry on the viewport scroller that Base UI measures; subtracting space again inside `#root` conflicts with its native-scrollbar compensation. Restore it after the last sheet unmounts, including overlapping navigation/Appearance transitions. Base UI owns scroll locking, focus and dismissal. Verify background coordinates throughout open/close with native scrollbars enabled, as well as painting and hit testing at the outer edge: the root gutter can clip both. See [MDN scrollbar-gutter](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/scrollbar-gutter) and [Base UI Dialog](https://base-ui.com/react/components/dialog).
- Project details B uses a scrollable composition: status near the description, owner/due-date properties, then a subtly outlined progress group with the task metric, percentage, progress bar, completion consequence and action. The action travels with progress rather than being detached in a bottom footer. Zero-task projects show No tasks without an indeterminate bar. Completion updates the record and an existing polite status region beside the action. It does not insert feedback into the page above the scrolled table. The completed action retains keyboard focus with `focusableWhenDisabled`; the shared Button style exposes the disabled appearance for both native and ARIA-disabled buttons.
- Closing project details returns to the opening control when it remains available. If filtering removed that control, the host supplies the Projects region as the fallback; the primitive can focus its first available control. Keep the page's scroll position. Verify the whole open → act → observe → close sequence from the person's actual working position.
- Feedback belongs to the active workflow. Creation opens the new record's details with a creation confirmation in the sheet description, even when table filters exclude it. Demo reset confirms beside its sidebar control, including inside mobile navigation; the next record mutation clears that acknowledgement. Neither action inserts a page-top banner. Appearance saves, restores and storage failures report in its persistent footer; a storage failure changes the header's persistence claim too.
- Project details and Appearance share `panel-sheet`, `panel-scroll` and `panel-feedback`. Appearance retains a persistent `panel-footer`; Project details groups its action and feedback with progress in the scrollable body. Empty live regions stay available to assistive technology without reserving visible space. Do not add transient toasts or duplicate announcements where the resulting view or an in-context status already communicates the outcome; a toast is justified only when it adds a way back (Undo), as Mark complete does.
- When creation or search hands off to project details, the host retains the original page opener. The closing dialog suppresses its own return-focus operation so it does not compete with the newly opened sheet. Cancel/Escape keeps ordinary return-focus behavior. Clearing empty table results focuses the surviving search field; a clear/reset button that becomes disabled retains useful keyboard focus. These follow the [WAI dialog focus guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) and [status-message guidance](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).

## Theme preference and preview

### Type and spacing baseline

The roles below apply to the page and its overlays. They are rem-based project defaults, not an accessibility-mandated count of sizes. Assign a role from the information's purpose before choosing a value; adding a role requires an actual information need. User font choice changes the family, preserving the roles and natural reflow.

| Role              | Default / line height               | Application and rationale                                                                                                       |
| ----------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Metadata          | 12px / 1.5                          | Dates, counts, chart ticks and secondary annotations. Never use it to make an important control fit.                            |
| Body and controls | 14px / 1.5                          | Content, field/detail labels, choices and actions; muted color distinguishes supporting content without inventing another size. |
| Section heading   | 16px / 1.375                        | Card, dialog and panel titles at weight 600. Mobile current-page context uses the same size at weight 500.                      |
| Page heading      | 28px, 24px on narrow screens / 1.25 | The page's primary heading, weight 600.                                                                                         |
| Metric            | 32px / 1.2                          | Comparable snapshot values and chart total, weight 600 and tabular numerals.                                                    |

Editable inputs use 14px with a fine pointer and 16px when the primary pointer is coarse, for legible touch entry and mobile browser behavior. A narrow desktop window alone does not enlarge fields. Field legends use the section size at medium weight as labels for related controls. The wordmark is a separate brand treatment (24.8px/650), not another content heading. Regular text uses 400, labels/actions 500 and headings/emphasized values 600. The primitive owns these treatments; feature code chooses semantic roles and composition.

Spacing uses Tailwind's 0.25rem unit and named relationship tokens: `--control-gap` for controls, `--card-padding` for card insets, `--panel-padding` for panel insets, `--section-gap` and `--page-padding` for the shell/page. A border, chart plot margin or avatar timeline offset can have a geometric purpose outside that scale. Equivalent card edges, controls and numeric emphasis share their owners; arbitrary fractional adjustments are not a separate spacing system.

The page's top and side insets use the same `--page-padding`. Its opening heading uses `text-box: trim-start cap alphabetic` so font leading does not add a visible extra band above the title. Preserve normal line spacing within wrapped headings and below them; do not compensate by reducing page padding or adding font-specific offsets. This is a progressive enhancement: older browsers without [text-box trimming](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-box-trim) retain normal heading leading.

Metadata remains readable supporting information. Consequential feedback and Appearance choices use the body role. Long user-entered project titles wrap in the activity feed and details sheet; the table may truncate the name because opening the record exposes its complete value.

Density controls both minimum heights and vertical padding through shared tokens. Comfortable uses 36px standard / 32px small controls and 4px vertical padding; Compact uses 32px / 28px and 2px padding. This follows the 32px toolbar controls in [dashboard-01](https://ui.shadcn.com/blocks) and the installed Base Nova 32px/28px size scale. Text size and line height stay unchanged. Inputs, Buttons and Select triggers consume the same density values; textareas use twice the vertical padding. When the primary pointer is coarse, retain 44px control minimums in both densities. Optional touch hardware does not enlarge every control in a mouse-first interface. A narrow fine-pointer viewport keeps the ordinary 36/32px standard-control scale. These are minimums: wrapped or enlarged content can increase height.

Input Groups own the outer height. Inline addons contribute no vertical padding; their buttons fit inside the shell's borders, rather than adding independent height plus padding that overflows the field. Button and Toggle sizing comes from their `size` variants, so a link styled with `buttonVariants({ size })` matches a Button of that size. `ui-button` and `data-size` remain stable hooks for contextual rules (Input Group addons, panel footers), because Base UI composition can replace `data-slot` on a trigger or close control. Check composite controls as well as standalone primitives when changing density. Icon-only header controls have equal hit areas, with `--control-gap` (8px) between controls. Page gutters are separate tokens: 16px on mobile, so edge spacing and inter-control spacing intentionally serve different roles.

The [density contract and complete Overview inventory](density.md) owns which dimensions respond to Comfortable/Compact and which deliberately stay stable. `--content-gap` (16/12px), `--stack-gap` (20/16px), `--item-padding` (12/8px) and `--navigation-height` (40/36px) connect internal spacing, form/list groups and working rows. Card insets use 20/16px and panel/dialog insets use 24/20px; narrow-screen insets stay 16px. Typography, semantic glyphs, badges, avatars, column widths and minimum chart/reading areas stay stable. Do not implement density by scaling the whole page or introducing component-specific exceptions without a content reason.

`--card-padding` gives header, body and footer a common inset. The completion chart's total and unit form its heading (for example, “68 tasks completed”), replacing the redundant “Task completion” title and separate summary. The period selector and exact date range form a second group, with the date inline before and programmatically describing the selector. The groups share the first header row where space permits. On narrow screens, dates and selector occupy one band below the total; the date can wrap between its two endpoints. Enlarged text can wrap the group when its content no longer fits, without shrinking type. This groups the result separately from the control that defines its scope. Chart and activity footer controls share a baseline and bottom inset. Recent activity places its event count at the trailing edge of the heading row, aligned on the text baseline with the shared control gap; allow wrapping when content needs it. Its Show all activity / Show recent action is centered in the footer. Activity actor, action and project link form one flowing sentence; the project link must not be forced into a separate block. Natural wrapping follows available width, and the timestamp remains a separate metadata line. Header, feed text and footer retain the card inset. The native activity scrollbar sits closer to the outer edge at the 8px control gap and uses the platform thin width to recover reading space. It remains visible when needed and accessible by wheel, touch and keyboard. Activity previews four events and can reveal all fixture events without resizing its card: a bounded viewport scrolls with keyboard or pointer and retains its scrollbar gutter. Native wheel scrolling continues into the page when the feed fits or reaches its boundary; do not create a dead wheel zone with scroll containment. The 24rem minimum activity body accommodates the four-event preview; content may still scroll when text wraps or is enlarged.

Activity overflow uses a soft transparency gradient over at most 2rem at each scrollable edge. The fade shrinks with the remaining scroll distance and disappears at an endpoint or when content fits. A separate opaque mask preserves the native scrollbar; header and footer stay outside the effect. Observe both viewport and list resizing so wrapping, font changes and expansion update the fade. Scroll padding keeps focused links clear of faded edges; forced colors disables the decorative mask. This uses [CSS gradient masking](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/mask-image), without adding a surface color or blurring readable content throughout the list.

A scroll container that clips horizontally must also be a containing block (`position: relative`). Otherwise absolutely positioned descendants, such as `sr-only` text, take their position from an ancestor outside it, escape the clipping and widen the page. The Projects board lanes did this at phone width (2026-09-29). When measuring overflow, look for positioned elements inside scrollers as well as wide elements outside them.

Desktop navigation can collapse to a 72px icon rail. Its actions keep accessible names and show tooltips on hover and keyboard focus. The header toggle uses the plain Lucide `PanelLeft` icon, matching the [shadcn SidebarTrigger](https://ui.shadcn.com/docs/components/base/sidebar#sidebartrigger), and stays transparent at rest in both states. Preserve hover feedback, the focus ring and the changing Expand/Collapse accessible label; `aria-expanded` describes the sidebar, not a selected toolbar action. The mobile navigation remains a separate full-label sheet. Its brand/Close row uses normal layout; when the wordmark cannot fit beside Close, retain the linked brand symbol and accessible name. Navigation labels and demo actions wrap rather than extending beyond the sheet. Collapse state belongs to the mounted shell; reload restores the expanded default and does not modify saved appearance preferences.

Content enlargement may wrap the header and card actions. The shell measures its actual sticky-header height for document anchor clearance. The Overview metric strip becomes two columns on narrow screens, with the divider and padding dropped at each row start. Details label/value pairs and Appearance choices also wrap according to available space. Charts resolve their metadata font to pixel measurements for SVG axes, recalculate when font/size changes or finishes loading, and let the numeric axis measure its own width. The date axis chooses evenly spaced dates from the end using measured label width and plot space, reserving half a label at the endpoints. This uses public Recharts props because its automatic tick cache does not include the inherited font family. Do not shrink chart text to conceal overflow. The daily data view remains available when a narrow plot displays fewer date ticks.

In progress uses independent `--in-progress`/`--in-progress-soft` tokens, just as Completed and In review use success and warning roles. Changing the accent changes brand emphasis, not the meaning of project states. Light popovers share the card foreground; dark popovers retain their elevated surface with the shared foreground. Chart axis values explicitly consume muted foreground through the chart primitive; verify the rendered Recharts markup after library changes so fallback colors cannot bypass the theme. Tooltips keep an explicit gap between series labels and values even when their width follows content.

Keep these axes independent: named preset, color mode (light/dark/system), density and permitted typography/radius options. “System” resolves color mode; it is not another palette. Reduced motion and forced colors come from user/environment preferences.

### Implemented interface fonts

Appearance provides one interface-font selector: Geist (default), Inter, Source Sans 3 and System. This scope was confirmed by the user. Headings, body text, controls, chart labels and portalled overlays share the choice; code/monospace roles remain separate. System uses the device's UI stack, so its appearance varies by operating system. Changing font does not change the type scale, density, weight hierarchy or spacing tokens; natural text reflow is expected.

- `src/kit/theme/fonts.ts` is the catalog of stable IDs, display names and fallback stacks. `InterfaceFont` derives from the catalog instead of maintaining a second list.
- `src/kit/styles/fonts.css` imports the self-hosted Fontsource variable faces. Vite emits the font assets with the app. There are no runtime requests to a font CDN. Browsers load the used faces/subsets; opening the picker renders the names in their actual faces and can load those preview fonts. Do not preload every alternative.
- `ThemeSettings.font` stores only the selected ID in the existing theme preference. `applyTheme` sets `--font-interface` on the document root before React renders and whenever the preference changes. Tailwind's sans and heading roles reference that token, including inside portals. Missing or unsupported saved font IDs resolve to Geist; the rest of the saved theme remains intact.
- `src/kit/theme/font-selector.tsx` composes a labelled shadcn Select. It receives a value and change callback; it owns neither storage nor global styling. Restore defaults restores Geist through the existing theme owner.

To add a family: add its approved self-hosted font package, import its normal variable face in `fonts.css`, add its ID/label/fallback stack to the catalog and retain its supplied license in `public/font-licenses/`. The picker and persisted-value lookup then use it without new page-level font rules. Check the required weights, character coverage, readable fallback, and actual page/overlay layout. [Fontsource variable font imports](https://fontsource.org/docs/getting-started/variable) and [Tailwind font-family tokens](https://tailwindcss.com/docs/font-family) describe the underlying mechanisms.

### Preview and saved preferences

Preference precedence: explicit temporary preview, saved user preference, shipped default. OS preference resolves system mode. A temporary preview never silently overwrites a saved preset. Restore/reset must be visible and reversible.

The Appearance panel edits site preferences. The implemented [theme playground](pages/reference/themes.md) owns temporary token edits and named local presets, reusing `applyTheme` in a same-origin preview document. Its root and portalled overlays share the draft. Preview appearance controls report back to the editor and never call site-preference persistence. The outer editor retains its normal appearance so an unreadable draft remains recoverable.

Applying a preview across demo pages keeps the preference in a demo-specific namespace. In a server-rendered implementation, initial rendering must resolve that preference early enough to avoid a mismatched first paint and hydration. Do not spread theme-reading logic into individual components.

**Installable themes (2026-09-28).** A theme leaves the playground as a shadcn `registry:theme` item that installs its own file, `src/kit/styles/themes/<name>.css`, imported from `kit.css` after `theme.css`. `theme.css` stays the owner of the defaults; installed themes are overrides in their own files, one per theme, and can be removed by deleting the file and its import. They use `:root:not(.dark), :root:not(.dark)[data-accent]` for light and `:root.dark, :root.dark[data-accent]` for dark, which outrank the defaults and every accent block without relying on load order between modes. Verified with shadcn CLI 4.21: a plain `cssVars` item lands inside `@layer base` in `kit.css`, where the unlayered kit tokens beat it, so it would have no effect. Because an installed theme sets the brand for every accent, the Appearance accent swatches no longer match the page; products that install a theme should drop the accent choice or register the theme as an accent.

**Generated palettes (2026-09-28).** `generatePalette` in `src/kit/theme/palette.ts` turns one seed color into the brand tokens for both modes. Starting points follow the shipped accents (light: the seed itself, soft fills at L 0.95; dark: L 0.76 with chroma capped at 0.12, soft fills at L 0.28); lightness then moves until links reach 4.5:1 on the background and brand fills and soft fills reach 4.5:1 with their text. The optional neutral tint keeps each grey's lightness and alpha and moves its hue to the seed, with chroma peaking at mid-lightness so surfaces stay nearly neutral; a grey seed leaves greys untinted. Only greys that are literal values in `theme.css` are tinted; tokens defined as `var(...)` follow them. Categorical hues and status colors never change.

Version 1 JSON contains the preset name, all appearance choices and both resolved color palettes. Import validates supported settings and absolute CSS colors through Culori before changing the draft; saving is explicit. CSS exports the same color values and font family for integration after the existing Tandem styles. Its header specifies the root attributes and mode class; responsive geometry remains owned by the shared styles. CSS is not an independent replacement stylesheet or an import format. Shipped presets come from the accent catalog (`src/kit/theme/accents.ts`), which also feeds the Appearance choices, saved-preference parsing and preset validation. CSS remains the palette-value owner: each accent has a light and a dark `[data-accent]` block in `theme.css`, written so any element can carry an accent (swatches use this to show the real `--brand`). `accents.test.ts` fails when the catalog and the CSS disagree.


## Narrow-screen composition

Width, input method and density are independent axes. Recompose first, then reduce expendable spacing; preserve content, readable type and interaction targets. These are local design decisions informed by [WCAG target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) (24px AA minimum with exceptions, not a blanket 44px rule) and [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html). Do not treat a passing overflow measurement as a visual review.

| Relationship | Narrow-screen rule | Preserved invariant |
| --- | --- | --- |
| Page and cards | 16px horizontal gutters/insets; 20/16px section gaps and 16/12px internal gaps by density. | Body 14px, metadata 12px, icons and data meaning remain stable. |
| Header actions | Align the outer icon glyphs with the page gutter; let their larger hit boxes use that gutter, with 4px clearance for focus. | Equal targets and 8px between controls; 56px header minimum. |
| Page heading | Title on its own row, snapshot/date and New project beside each other below. Metadata wraps within its share of the row. | Full date and action label; large text may require another row. |
| Chart | Total first; dates and period control share the next band with 8px between them. Dates break between endpoints before the selector moves. | Standard control sizing, full range, stable plot readability and data view. |
| Table toolbar | Search uses the available row; Status, Owner and icon-only Reset form the following group. An active selection count replaces the decorative plus. | Named controls, visible counts, Reset accessible name/title; no reserved invisible labels. |
| Pagination | Result count and Rows selector share a row; Previous, page count and Next occupy the next row. First/Last remain on wide screens. With enlarged text, the counter moves above the paired arrows when its container is too narrow. | All pages remain reachable, full accessible Rows per page label, disabled-state feedback. |
| Sheets and dialogs | 16px horizontal inset, 8px top/title-row inset. Form gaps use the content token; footer actions stay inline while they fit. | Close remains in normal layout with its full target; content can scroll and text can grow. |
| Search | Use the same input height/type rules as other editable fields; results use shared small-control rows. | Keyboard navigation, focus indicator and visible Close remain intact. |

At 320 CSS px, review both default and enlarged text, including filtered controls and portalled menus. Also inspect a touch-emulated phone width and the unchanged desktop composition. Do not use global page zoom, tiny control labels, ellipses or hidden date information to force a one-line layout.

## Practical proof of customization

Acceptance: change brand color, font, radius and density in the playground; inspect a public hero, a settings form, the project table, a chart and an open menu/dialog. The intended changes should propagate without editing page code. Reload preserves saved choices; reset restores shipped defaults.

Report contrast failures for actual foreground/background pairs, including focus and interactive states. Do not silently “fix” the user's selected colors, and do not claim an automated contrast result establishes complete accessibility. Shipped presets must pass the applicable quality checks before being presented as recommended presets.

New browser styling capabilities are optional until a support policy is set. The modern-web-guidance lookup suggests container style queries for reactive density, but recommends selectors for essential functionality across broader browser support. The initial design can use semantic custom properties and root preference attributes without depending on that newer feature.

## Tooltips and explanatory text

Use the shared `TextHint` for a term whose brief supplementary explanation is useful on demand. Its dotted underline signals that explanation; preserve the surrounding typography. Ordinary links keep link styling, and routine labels do not acquire hints without useful content. Required instructions, errors and consequential action details remain visible in their owning flow.

Text hints use the existing Base UI Popover with hover opening, following its [infotip guidance](https://base-ui.com/react/components/tooltip#infotips). The trigger is also a button for touch, Enter and Space; Escape and outside interaction dismiss it. Content inherits shared typography, theme and overlay positioning. Use the Tooltip primitive for an existing control's concise label, with a matching accessible name. Longer or interactive help belongs in a popover, dialog or guide according to the task.

The reference example is `/reference/components/tooltip` (SYS-07); Overview's due-soon metric demonstrates a contextual explanation.
